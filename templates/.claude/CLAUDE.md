# CLAUDE.md

本文件是 Claude Code 在真实影刀项目中的协作规则，建议放在：

```text
.claude/CLAUDE.md
```

如果项目根目录同时存在 `AGENTS.md`，则以根目录 `AGENTS.md` 为主规则入口；本文件用于让 Claude Code 读取同一套核心协作偏好。

影刀 xbot / AI 开发知识库默认位于 `~\Desktop\影刀xAI开发指南`，该目录用于查规则、查 API、查示例和调用 `shadowbot_sync_tool.py`，不是实际业务项目源码目录。

真实开发时，Claude Code 应直接在影刀项目目录工作；知识库目录和影刀项目目录不是同一个目录，不要把 `~\Desktop\影刀xAI开发指南` 当成业务项目根目录。

适用场景：真实影刀项目中的代码生成、代码修改、Bug 修复、流程补全、影刀编码版开发。

核心目标：**最小改动、简单直接、可读可维护、不要猜 API、不要无关重构。**

影刀项目写日志时，**禁止使用 Python 标准 `logging`**；只允许使用 `from xbot.app import logging`。出现 `import logging`、`logging.basicConfig(...)`、`logging.getLogger(...)`、`logger.exception(...)` 都视为错误实现，因为标准 `logging` 不会进入影刀日志面板。

---

## 1. 总体原则

1. 优先保证代码能运行，再考虑优化。
2. 优先简单、直接、容易审查的实现方式。
3. 不为“高级”“规范”“通用”而引入复杂设计。
4. 只解决当前任务明确要求的问题。
5. 不提前处理未出现、未验证、低概率的场景。
6. 不做与当前需求无关的重构、改名、格式化或结构调整。
7. 每一处改动都必须能对应当前需求。
8. 如果发现潜在问题，可以指出，但不要擅自扩大修改范围。
9. 不要编造不存在的功能、命令、目录、文件、XPath 或 API。
10. 不确定的地方必须标注“需运行验证”，不要自行推断。

---

## 2. Claude Code 执行流程

处理任务时按以下顺序执行：

1. 先阅读用户需求。
2. 再阅读当前项目相关文件。
3. 确认当前工作目录是真实影刀项目目录，不是知识库或模板库目录。
4. 判断需要修改哪些文件，以及哪些文件不能改。
5. 给出最小可行修改方案。
6. 修改代码。
7. 删除本次改动造成的不再使用的 import、变量或函数。
8. 运行能运行的本地检查。
9. 最终说明修改内容、验证方式、未验证项和待人工确认项。

处理 Bug 时按以下顺序：

1. 先复现或定位问题。
2. 再找当前代码中的确定证据。
3. 只修改与问题直接相关的位置。
4. 修改后说明验证方式。
5. 不要把旧项目经验、未确认框架行为套进当前问题。

---

## 3. 修改代码前必须确认

修改前先判断：

1. 当前问题是什么。
2. 证据来自哪里：报错、当前代码、文档、页面、用户描述。
3. 哪些文件 / 函数需要改。
4. 哪些内容不能改。
5. 最小可行修改是什么。
6. 修改后如何验证。

如果用户需求很明确，可以直接执行；如果存在关键歧义，先指出歧义并给出建议选择。

## 4. 代码风格

1. 代码要简单、直接、容易阅读。
2. 优先顺序式流程，不要为了少量逻辑拆很多函数。
3. 变量名直白，逻辑块清晰，数据流显式。
4. 临时变量可以短，但要直观，例如 `data`、`item`、`records`。
5. 不要使用 `x`、`tmp`、`obj` 这类过于抽象的变量名。
6. 保持现有项目风格，不要无关格式化整个文件。
7. 注释只解释关键业务逻辑、特殊页面逻辑或不直观的 API 行为。
8. 不要写解释 Python 基础语法的无意义注释。
9. 函数注释使用 Sphinx / reStructuredText 格式。
10. 单文件较长且函数较多时，可以用中文分块注释做导航，但不要借机重排无关代码。

示例：

```python
def load_cache(file_path):
    """读取缓存文件。

    :param file_path: 缓存文件路径
    :type file_path: str
    :return: 缓存数据
    :rtype: dict
    """
    ...
```

## 5. 函数、常量、类的使用规则

### 5.1 函数

默认不要为了“看起来规范”拆函数。某段逻辑只在一个地方使用时，优先直接内联写在调用处，不要单独封装。

只有满足以下情况之一时，才抽函数：

1. 代码量较多，内联后已经明显影响主流程阅读。
2. 逻辑本身较复杂，需要单独命名降低理解成本。
3. 后续已经明确会复用，而不是“可能会复用”。
4. 当前项目已有类似结构，需要保持风格一致。

以下情况默认不要抽函数：

1. 函数只在一个地方使用，且内联后主流程更直观。
2. 函数体只有 1 条语句。
3. 抽函数后反而需要更多参数传递，阅读更绕。
4. 单次调用、逻辑很短、且不代表明确业务步骤。

函数优先接收自己实际需要的具体值；如果只用 dict 里的少数字段，不要把整个 dict 传进去再拆。只有把 dict 当完整业务实体使用，或只是原样转发给下层时，才直接传容器。

### 5.2 常量

默认不要为了“看起来像常量”就提取常量。

只有满足以下情况之一时，才提常量：

1. 多处复用。
2. 属于公共配置。
3. 提取后明显更清楚。
4. 用户明确要求集中配置。

单次使用的 URL、XPath、字段名、固定字符串、小表达式，默认直接写在使用处。

展示值和业务值一致时，不要额外增加翻译函数、映射表或间接层。

### 5.3 类 / 管理器

默认不要新增类、管理器、抽象层。

只有满足以下情况之一时，才使用类：

1. 现有项目已经使用同类结构。
2. 状态复杂到函数无法清楚表达。
3. 用户明确要求长期架构设计。

### 5.4 配置层

默认不要新增复杂配置层。

但以下情况可以使用简单 `config.py`：

1. 用户明确要求使用 `config.py`。
2. 账号、路径、webhook、店铺列表等需要集中维护。
3. 多平台、多店铺、多环境配置明显会重复使用。

不要为了少量一次性参数设计复杂配置系统。

不要为了单次遍历构造中间分层结构；后续流程不需要的结构不要提前设计。

## 6. 返回值解耦规则

1. 函数返回值优先只承载当前方法的主业务结果或不可逆的现场观测，不要为了后续计数、日志、汇总、通知等收尾步骤，顺手夹带额外统计信息。
2. 如果这些后置信息可以从主业务结果现场计算得到，就在最终使用处再算，不要提前耦合到当前函数的返回值里。
3. 只有当后置所需信息无法从主业务结果可靠推导，或现算会丢失必要上下文时，才考虑额外返回辅助统计，并明确保留原因。
4. 扫描、采集、业务处理函数默认返回主结果即可；后面的计数、日志、汇总优先基于主结果计算，不要默认同时返回 `stats`、`summary`、`count_map`。

---

## 7. 输入、异常与兼容规则

1. 调用方已经明确约定入参类型或记录结构时，被调函数直接按约定使用。
2. 不要在业务逻辑中反复写 `isinstance`、`dict(...)`、空结构回退等防御性归一化。
3. 如果输入形态确实不确定，只允许在边界统一归一化一次。
4. 进入业务逻辑后，不要继续重复判断和兜底。
5. 异常处理只覆盖当前业务明确需要处理的失败情况。
6. 不要默认添加复杂异常体系、重试框架、日志框架或配置层。
7. 捕获异常时必须保留关键错误信息。
8. 不要吞异常不说明。
9. 不要主动为未知旧接口或旧缓存增加兼容。
10. 已有代码中已经存在的兼容逻辑，不要无关删除。
11. 数据写入类任务要让失败隔离粒度和落盘时机对齐：逐项捕获异常就逐项保存，整批统一处理才在批量末尾统一保存。

## 8. 影刀项目规则

1. 真实影刀项目由人类先在影刀编辑器中创建，Claude Code 不负责直接创建 `apps` 目录下的新项目。
2. Claude Code 应直接将真实影刀项目目录作为工作根目录打开，不要把知识库仓库当成业务项目目录。
3. 影刀项目代码入口通常为 `main(args)`。
4. 常见初始化导入包括：

```python
import xbot
from . import package
from .package import variables as glv
```

5. `args` 中使用的流程参数名必须由人类先在影刀编辑器中配置，Claude Code 不应自行猜测参数名。
6. 编码版参数、市场指令参数必须以文档或源码为准，不要根据可视化界面中文选项猜测。
7. 可视化界面能跑，不代表编码版参数一致。
8. 测试通常由人类在影刀编辑器中完成；Claude Code 根据测试反馈继续修改。
9. 不要把“已同步”写成“已在编辑器内验证通过”。

## 9. 影刀 API 与知识库使用规则

写影刀编码版代码前，优先查知识库中的 `xbot-api-docs`。

建议查询顺序：

1. 通用 API：`xbot-api-docs`
2. 浏览器操作：`xbot-api-docs/docs/browser.md`
3. 表格操作：`xbot-api-docs/docs/excel.md`
4. 市场指令参数：`xbot-api-docs/docs/debug/market-extension-source.md`

如果当前工作区没有 `xbot-api-docs` 或相关文档：

1. 不要编造 API 行为。
2. 先查看当前项目已有代码。
3. 必要时使用 `inspect.signature()`、`inspect.getfile()` 查看真实实现。
4. 仍不确定时，标注“需运行验证”。

不确定 API 行为时，不要猜。

---

## 10. 浏览器与网页自动化规则

1. 涉及浏览器、URL、网页业务功能时，优先使用 `xbot.web` 及其浏览器对象能力。
2. 页面自动化、登录态、Cookie、下载、网络监听优先使用影刀浏览器能力处理。
3. 除非用户明确要求接口方式，或当前项目已有接口调用方式，否则不要使用 `requests`、`httpx`、`aiohttp`、`urllib` 等网络库处理网页业务。
4. 能用元素操作就不要优先坐标点击。
5. 中文或长文本输入优先考虑剪贴板输入。
6. 页面字段、价格口径、按钮含义必须以当前业务规则为准，不要自行推断。
7. XPath、CSS、页面接口、按钮状态未验证时，必须标注“需运行验证”。
8. 价格采集优先使用 XPath、CSS、页面接口或明确规则取数，不要让 Claude Code 自由猜页面价格。

---

## 11. Excel / 表格处理规则

1. 表格大量写入时，优先考虑二维数组批量写入。
2. 不要逐单元格大量循环写入，除非数据量很小或当前项目只能这样做。
3. 读取和写入范围必须明确。
4. 写入前是否清空原内容，必须以用户需求或当前项目规则为准。
5. 不要自行改变 sheet 名、字段名、列顺序。
6. 表格路径、sheet 名、日期规则不确定时，先标注“需运行验证”。

---

## 12. 市场指令排查规则

当市场指令文档不清楚、参数不明确、可视化能跑但编码版异常时：

1. 先用 `inspect.signature()` 查看包装层参数。
2. 再用 `inspect.getfile()` 定位 `xbot_extensions` 安装目录。
3. 查看 `__init__.py`、`_core.py` 或其他真实实现文件。
4. 以源码里的真实判断逻辑为准。
5. 不要根据界面中文选项猜编码版参数。

示例：

如果源码判断：

```python
close_type == "click"
```

编码版就应该传：

```python
"click"
```

不要传：

```python
"点击"
```

## 14. 钉钉 AI 表格规则

1. 钉钉 AI 表格记录列表默认从以下路径取：

```python
records = result.get("data", {}).get("records")
```

不要直接从顶层取：

```python
records = result.get("records")
```

2. 钉钉 AI 表格记录默认按以下方式取字段：

```python
fields = record["fields"]
```

3. 多选字段先按以下结构理解显示值：

```python
{"name": "...", "id": "..."}
```

4. 真正开发前必须实测字段真实结构。
5. 不要自行猜测钉钉字段返回结构。
6. 通知结果列表建议使用 `notify_records` 这类直观命名，避免和表格回写 `records` 混淆。
7. 涉及“业务处理 + 通知汇总”时，优先让业务模块返回结果列表，由入口流程统一收集，通知模块再做分组和格式化。

## 15. 同步与收尾规则

开发完成后，真实影刀项目中修改 `.py` 文件后，需要运行知识库根目录的 `shadowbot_sync_tool.py prepare` 同步收尾。

同步前先核对：

1. `main(args)` 入口结构。
2. `args` 参数名。
3. `package.variables` 变量名。
4. 元素库名称。
5. 资源文件名称。
6. 目标项目环境是否已安装所需市场指令。
7. 是否只修改了当前需求相关代码。

`shadowbot_sync_tool.py prepare` 只接收 `.py` 文件作为输入。

不要把 `package.json` 等非 Python 文件直接传给 `prepare`。

`prepare` 会顺带处理 `package.json` 的 flow 更新和编译，但不会自动备份项目。

如需备份，需要显式调用：

```powershell
python C:\Users\Administrator\Desktop\影刀xAI开发指南\shadowbot_sync_tool.py --project-dir "%LOCALAPPDATA%\ShadowBot\users\<user_id>\apps\<app_id>" backup
```

最小同步示例：

```powershell
python C:\Users\Administrator\Desktop\影刀xAI开发指南\shadowbot_sync_tool.py --project-dir "%LOCALAPPDATA%\ShadowBot\users\<user_id>\apps\<app_id>" prepare main.py
```

## 18. 自检门禁

写代码前先判断：

1. 要不要新函数：默认不要为了“看起来规范”拆函数。某段逻辑只在一个地方使用时，优先直接内联写在调用处；只有在代码量较多、内联后明显影响主流程阅读，逻辑本身较复杂、需要单独命名降低理解成本，或后续已经明确会复用时，才抽函数。
2. 要不要新常量：只有多处复用、属于公共配置、或提取后明显更清楚时才提常量。
3. 要不要新类 / 管理器：默认不要，除非现有项目已经使用同类结构，或状态复杂到函数无法清楚表达。
4. 要不要配置层：默认不要新增复杂配置层；但用户明确要求 `config.py`，或账号、路径、webhook、店铺列表需要集中维护时，可以使用简单 `config.py`。
5. 要不要兼容多种输入：调用方已有约定时，直接按约定结构使用，不反复写防御性归一化。
6. 要不要传整个容器：函数优先接收自己实际需要的具体值；如果只用 dict 里的少数字段，不要把整个 dict 传进去再拆。
7. 要不要映射层：展示值和业务值本来一致时，不要额外加翻译函数、映射表或间接层。
8. 要不要提前分层：不要为了单次遍历构造中间分层结构；后续流程不需要的结构不要提前设计。
9. 要不要捕获异常：只有当前业务需要补充上下文、通知、截图或恢复流程时才捕获；捕获后必须保留关键错误信息。
10. 要不要重试 / 多候选兜底：默认不要，只有页面或接口已确认存在这种不稳定性时才加。
11. 要不要顺手改名 / 格式化 / 重排代码：默认不要，只改当前需求直接相关的行。

生成代码后再回看一遍：

1. 如果删掉某个抽象、常量或兜底分支后代码仍然清楚，就删掉它。
2. 如果内联后主流程更直观，就不要为了“结构更漂亮”再包一层函数。
3. 阅读性优先于工程化。


## 20. Claude Code 工具与协作补充

1. 搜索文件名、代码和文本时，优先使用 `rg` / `ripgrep`；不可用时再使用其他搜索工具。
2. 修改已有文件前，先阅读相关上下文；不要只凭文件名或旧经验直接改。
3. 手工改文件时优先使用补丁或编辑工具做最小 diff，避免无必要地整文件重写。
4. 不要用脚本批量改无关文件；确需批量处理时，先确认匹配范围只包含本次任务需要修改的文件。
5. 工作区可能已有用户改动；不要回滚、覆盖或清理不是本次任务产生的改动。
6. 不要执行 `git reset --hard`、`git checkout --` 等会丢弃改动的命令，除非用户明确要求。
7. 运行验证命令后，最终回复要说明关键结果；不要假设用户能看到终端输出。
8. 用户要求 code review / 审查时，先列问题，按严重程度排序，并给出文件和行号；如果没有发现问题，要明确说明未发现问题和剩余测试风险。
