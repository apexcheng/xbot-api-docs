# AGENTS.md

本文件用于真实影刀 xbot / 编码版项目，只保留执行任务时必须常驻的约束。详细示例和 API 事实仍以用户提供的知识库为准，不在项目内复制第二套文档。

核心原则：**最小改动、过程清楚、不猜 API、按风险验证。**

## 开始任务

1. 用户当前需求和项目已有业务逻辑、参数约定、数据口径优先。
2. 用户明确给出的 API 调用方式、XPath、字段名、参数名、路径、Sheet 名和业务规则视为已确认输入；没有直接冲突时不得擅自替换。
3. 只改与需求直接相关的内容，不做无关重构、格式化或结构调整；先读相关代码并保留用户已有改动。
4. 目标清楚时直接执行。只有新增完整功能、跨模块影响主流程、涉及未确认外部行为或高风险操作时，才做简短的“计划 → 执行 → 验证”。
5. 知识库只补足项目无法确认的部分。路径缺失且确实需要查证时请求正确位置，不猜固定路径。
6. 规则冲突时，选择改动更小、结构更简单、业务顺序更清楚、风险更低的方案。

## 代码结构与编程风格

本节是业务代码的硬约束，不因详细示例放在知识库中而减弱。

1. 自动化和数据处理默认使用自上而下的过程式主流程，让读取、判断、操作、写回、保存和通知顺序直接可见；业务步骤有明确先后时，代码保持同样顺序。
2. `run.py` 保留 `main(args)` 入口和主业务顺序；`config.py` 只放项目配置、配置路径或稳定静态设置；稳定且真正复用的能力沿用已有 `tool.py`、`utils.py`、`win_utils.py`，不为整理代码另建工具层。
3. 单次使用的 URL、XPath、CSS、字段名、按钮文案、状态值、简单属性、简单表达式和立即调用结果，默认在使用位置内联。只有需要复用、后续判断、表达式较复杂、命名能解释业务含义，或必须保留对象状态时才提取变量。
4. 单次使用的短逻辑和一两行的业务步骤默认就地表达，不因为“有独立业务含义”就拆函数。只有逻辑重复，或代码较长、业务边界清晰且抽出后主流程明显更易读时才提取函数或模块。
5. 函数只接收实际需要的具体值；只使用字典中少数字段时，不传整个 `dict` 或巨型 `context`。状态只保留跨步骤确实需要共享的部分。
6. 普通影刀业务流程默认不用类。只有存在明确对象生命周期、需要长期维护实例状态，或项目已有同类结构且沿用更简单时才使用类。
7. 优先使用普通变量、`if`、`for`、`try` 等直白写法；不使用会隐藏业务顺序的嵌套推导式、`lambda`、复杂映射、装饰器、生成器、动态调度或多层 wrapper。
8. 不新增无必要的 Service、Manager、Context、Registry、Factory、Dispatcher、Strategy 或大型配置层；不为未来需求预留未使用参数、分支、Hook、兼容层或扩展点。
9. 函数和方法调用在保持可读时写在一行，参数很多或结构复杂时正常换行。变量名直白表达业务含义；只给关键业务判断写中文注释。需要函数文档注释时使用 Sphinx / reStructuredText 格式。
10. 已知参数名时严格使用现有名称；新增 `args` 参数使用最小、直观、稳定的名称；输入形态不确定时只在 `main(args)` 边界归一化一次。
11. 异常处理只覆盖明确需要处理的失败，不静默吞错。直接继续失败时使用 `raise`；补充业务上下文时使用 `raise ... from exc`；`traceback.format_exc()` 用于记录异常现场，`raise` / `raise ... from exc` 用于异常传播，上层会统一记录完整堆栈时中间层不重复记录；异常路径的收尾不得覆盖原业务异常。
12. 健壮性只处理真实可能且业务明确要求处理的失败。正常业务 API 已能明确抛错时，直接依赖该失败，不增加等价的前置校验、全量预检、重复读取或多套兜底逻辑。
13. 旧代码可以提供线索，但不能证明设计正确。不要继续扩散过度封装、重复防御、无意义中间变量、一次性函数或历史兼容结构。

需要查看变量内联、函数边界和异常收尾的完整判断与示例时，读取知识库 `docs/coding-style.md`；以上规则已足以约束普通小改。

## xbot 与知识库

1. 不根据通用 Python 经验、旧项目记忆或名称相似度猜 xbot API、市场指令、页面字段、XPath 或命令。
2. 用户已给出或当前代码已确认的稳定调用优先原样沿用。只有新增、修改或排查相关行为且证据不足时，才按知识库 `llms.txt` 读取事实页的相关章节。
3. 网页相关问题查 `browser.md`，Win32 查 `win32.md`，Excel / WPS 查 `excel.md`；不机械加载与当前改动无关的全文。
4. URL、路径、Sheet 名、`args` 字段、XPath 和 API 参数必须来自用户、真实项目或可核验证据，不用假值拼成看似可运行的实现。
5. 网页业务默认使用 `xbot.web`；等待明确异步条件，不靠不断增加固定 `sleep`；已有元素或选择器时不优先坐标操作。
6. 影刀日志使用 `from xbot.app import logging`；动态内容使用完整 f-string，异常堆栈使用 `traceback.format_exc()`。
7. 依赖真实影刀、WPS、浏览器或页面才能确认的行为标记“需运行验证”。读取旧版可视化项目时使用 `.agents/skills/xbot-visual-flow-reader/SKILL.md`，纯 Python 任务不触发。

## 验证与同步

1. 按风险做最小必要验证；默认不新增测试或运行无关全量检查。高风险写入先确认范围和回退方式。
2. `shadowbot_sync_tool.py` 与 `package.json` 位于项目根目录。新增 `.py` 文件后默认运行 `python shadowbot_sync_tool.py`；只修改已有 `.py` 文件时，仅在用户明确要求同步时运行。
3. 同步脚本自动扫描 Python 文件，不接收文件列表或 `prepare` 子命令；同步不是 Git 操作，成功也不等于影刀编辑器内运行验证。
4. 验证失败时先区分代码、环境、依赖和路径问题，不为通过无关检查扩大修改。

## 安全与汇报

1. 不隐藏副作用，不通过吞异常、静默失败或模糊返回值让主流程看起来成功。
2. 不提交账号、密码、Token、Cookie、Webhook、客户数据或未公开地址；示例和日志必须脱敏。
3. 不为单次任务创建临时进度 Markdown；长期业务规则和设计决策写入项目已有正式文档。
4. 完成后简短说明修改内容和实际验证；只有未执行项会影响结果判断或本应执行但受限时才特别说明。新增 `args` 参数时列出参数名、含义和建议类型。
