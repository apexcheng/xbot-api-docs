# AGENTS.md

本文件用于真实影刀 xbot / 编码版项目。

核心原则：**最小改动、过程清楚、不猜 API、按风险验证。**

## 开始任务

1. 用户当前需求、项目已有业务逻辑、参数约定和数据口径优先。
2. 用户明确给出的 API 调用方式、XPath、字段名、参数名、路径、Sheet 名、业务规则和数据口径，视为当前任务的已确认输入；除非用户要求核验，或真实代码、源码、运行证据出现直接冲突，否则不得因为知识库未记录、写法不同或 Agent 认为“更标准”就擅自替换。
3. 知识库用于补足用户和真实项目没有提供、无法确认的部分，不用于覆盖已经明确的项目事实。发现明确输入与可核验证据冲突且会影响实现时，停止相关修改并向用户说明冲突，不自行选一边改掉。
4. 只改与需求直接相关的内容，不做无关重构、格式化或结构调整。
5. 目标清楚时直接执行；复杂任务只做“简短计划 → 执行 → 验证”。
6. 知识库路径由用户或项目提供。路径缺失时请求正确位置，不猜固定路径。
7. 先读当前项目代码；只有新增或无法确认 xbot API、市场指令或页面行为时，才按知识库的 `llms.txt` 查对应页面。
8. 新建或补全项目时读取知识库 `docs/base-project-skeleton.md`；多个必需数据源写入同一工作簿时读取 `docs/multi-source-report-safety.md`。
9. 规则冲突且没有更高优先级的明确要求时，优先选择改动更小、结构更简单、真实业务顺序更清楚、风险更低的方案；不得为了“更规范”或“更工程化”擅自更换实现路线。
10. 需求或取舍不清楚、新增完整功能/流程/数据结构、跨模块并影响主流程、涉及无法从当前代码确认的新 API/市场指令/页面行为，或涉及批量写入、删除、迁移、发布、权限等高风险操作时，按复杂任务处理，只做“简短计划 → 执行 → 验证”。

## 实现方式

1. 自动化和数据处理默认采用自上而下的过程式主流程，让读取、判断、操作、写回、保存和通知顺序直接可见。
2. 代码顺序尽量对应真实业务执行顺序；不要为了“更工程化”“更整洁”或形式上的复用制造额外跳转、隐藏真实执行顺序。
3. 单次使用的短逻辑默认就地写，不为了形式上的复用拆函数。
4. 单次调用的业务步骤，不因为“有独立业务含义”就抽函数。只有代码量较多、业务边界清晰且抽出后主流程明显更易读时，才为单次业务步骤抽函数；函数体只有一两行且只调用一次时不要封装。
5. 函数、模块或类只在实际复用、形成稳定公共能力，或确实能明显降低主流程理解成本时引入；文件较长本身不是拆函数或拆模块的理由。
6. 普通影刀业务流程默认不用类组织。只有存在明确对象生命周期、需要长期维护的实例状态，或当前项目已有同类结构且继续沿用更简单时才使用类。
7. 单次使用的 URL、XPath、CSS、字段名、按钮文案、状态值、提示语默认直接写在使用位置，不要仅为了“像常量”提取变量或常量。
8. 只使用一次、且只是承载字面量、简单属性、简单表达式或立即调用结果的局部变量，默认直接内联到实际使用位置；只有会被重复使用、需要后续读取或判断、表达式本身较复杂，或必须保留对象状态时才保留变量。
9. 能在使用位置直接读取或计算的值默认就地处理，不为了“统一管理”额外放入全局变量、`dict`、`context` 或长期中间状态。
10. 简单功能优先使用普通变量、`if`、`for`、`try` 等直白写法；不使用嵌套推导式、`lambda`、难懂的一行式、会隐藏执行顺序的动态调度、复杂映射、装饰器、生成器或多层 wrapper。
11. 函数和方法调用默认写在一行；只有参数很多、参数结构复杂或单行明显降低可读性时才换行。
12. 不新增无必要的 Service、Manager、Context、Registry、Factory、Dispatcher、Strategy、多层 wrapper、动态调度或大型配置系统；不要通过换一个类名继续引入同类抽象层。
13. 不为未来需求预留未使用参数、分支、Hook 或扩展点。
14. 变量名应直白表达业务含义，避免 `x`、`tmp`、`obj` 这类无语义名称；关键业务判断可以写中文注释，简单赋值、基础语法和显而易见的逻辑不要写解释性注释。
15. 异常处理只覆盖明确需要处理的失败；保留关键错误信息，不静默吞异常。捕获底层异常后，如果只是继续失败且没有增加新的业务上下文，直接 `raise`；如果需要补充当前业务步骤、字段名、XPath、订单号等定位信息并重新抛出，使用 `raise ... from exc` 保留原始异常链。不要为了形式统一做 `raise RuntimeError(str(exc)) from exc` 这类无意义包装，默认也不要用 `raise ... from None` 隐藏底层异常。
16. 关闭页面、工作簿、窗口、监听或停止加载等明确的收尾动作默认直接调用；需要保证业务异常时仍执行时放在 `finally`，对象可能未创建时只判断对象是否存在。不要为了“保险”给单纯收尾动作再套一层吞异常的 `try / except`。
17. 健壮性优先处理真实可能发生且业务明确要求处理的失败；正常业务 API 已经能够明确抛错时，默认直接依赖该失败，不再增加等价的前置校验、全量预检、重复读取、重复扫描或多套兜底逻辑。
18. 已有代码本身不是正确性的依据。旧代码中的过度封装、重复防御、无意义中间变量、一次性函数或历史兼容结构，不应仅因为“保持现有风格”继续扩散。
19. 稳定且真正复用的公共能力优先放入项目已有工具文件；已有 `tool.py`、`utils.py`、`win_utils.py` 等结构时沿用，不为统一命名或目录结构新增另一套工具层。
20. 不根据通用 Python 经验或旧项目记忆猜 API、XPath、页面字段、命令和市场指令参数。
21. 用户已经明确给出某个 API、XPath、字段、参数或调用形态时，修改与排错默认保持其原样；不要仅因知识库没有同一条记录，就改成名称相近或 Agent 更熟悉的另一套写法。
22. URL、文件路径、Sheet 名、`args` 字段、XPath、API 参数等关键值无法确认时，不为了产出“完整代码”而编造看似可运行的值；能继续实现的部分保留真实结构，并用明确的 TODO / “未确认”标记缺口。TODO 只能放在注释、说明或省略位置，不要把 `"TODO: ..."`、虚构的 `args.xxx`、假 URL、假路径、假 Sheet 名或假 XPath 作为可执行参数写进代码；也不要用 `None`、空字符串、示例值、默认值、`...` / `Ellipsis`、`<工作簿路径>`、`<XPath>`、`<...>` 这类占位表达式占据真实业务参数位置后继续生成看似完整的 Python，也不要 `pass` 后继续引用本应由未确认逻辑产生的变量。关键值缺失时应直接省略该调用、保留现有代码，或只用注释 / 非 Python 伪代码说明缺口；如果缺口阻止形成可运行代码，就只输出可确认且自身成立的代码片段，不强行拼成完整函数。
23. 用户要求“代码骨架 / 示例代码”但关键依赖值仍未确认时，Python 代码块只能包含语法和变量都自洽、可独立成立的已确认片段；未知步骤必须移到代码块外用普通文本伪代码说明。不得为了展示完整结构而虚构 `args["xxx"]`、`shop["url"]` 等字段，不得保留未定义变量，不得用 `...`、`pass`、占位返回值或占位调用把一个本来无法成立的 `main(args)` 拼出来。
24. 必须依赖真实影刀、WPS、浏览器或页面才能确认的行为，标记“需运行验证”。
25. 影刀日志统一使用 `from xbot.app import logging`，不使用 Python 标准 `logging`。日志动态内容优先用 f-string 拼成一个完整字符串；需要异常堆栈时使用 `traceback.format_exc()`，不要依赖 `logger.exception()`；影刀日志已有时间前缀，不重复拼接时间。
26. 网页业务默认使用 `xbot.web` 和浏览器对象能力；除非用户明确要求接口方式或项目已有稳定接口实现，不擅自改成 `requests`、`httpx`、`aiohttp`、`urllib` 等 HTTP 实现。
27. Code 流入口通常为 `main(args)`；已知参数名时严格使用已有名称；新增参数时使用最小、直观、稳定的名称；不同时兼容多个未经确认的参数名、字段名或输入结构；输入不确定时只在入口归一化一次。
28. 能用元素或选择器时不优先坐标点击；中文、长文本或输入法不稳定时优先考虑元素的 `clipboard_input()`；新增第三方依赖需要用户明确允许或项目已在使用。
29. 读取旧版影刀可视化编排项目时，使用 `.agents/skills/xbot-visual-flow-reader/SKILL.md`；纯 Python 任务不触发。

典型判断：

```python
# 单次使用，直接内联
page.find_by_xpath("//button[contains(., '下一页')]", timeout=3).click()

# 不要为了单次调用额外提变量或包装
# next_xpath = "//button[contains(., '下一页')]"
# page.find_by_xpath(next_xpath, timeout=3).click()
# def click_next(page): ...
```

如果业务要求“采当前页 → 写当前页 → 展示 → 下一页”，代码也应保持这个顺序；不要改成“先采集全部页面 → 最后统一写入”，除非用户明确要求改变业务流程。

## 验证与同步

1. 按风险做最小必要验证；默认不新增测试、不运行完整测试或全量检查。小改只检查相关路径，只验证当前真实业务会经过的数据、Sheet、配置和外部资源；高风险写入先确认范围与回退方式。
2. `shadowbot_sync_tool.py` 与 `package.json` 位于项目根目录。
3. 新增 `.py` 文件后默认运行 `python shadowbot_sync_tool.py`，用户明确要求暂不同步时除外。
4. 用户要求“同步影刀”或同类操作时，也执行该命令，即使只修改已有 `.py` 文件。
5. 同步不是 Git 提交、推送或普通文件复制。
6. 同步成功不等于已在影刀编辑器中运行验证。
7. 同步脚本自动扫描 Python 文件，不接收文件列表或 `prepare` 子命令。
8. 需要完整错误堆栈时使用 `traceback.format_exc()`；通用排错见知识库 `docs/troubleshooting.md`。
9. 验证只执行当前改动真正需要的检查。仅修改已有 `.py` 文件且用户未要求“同步影刀”时，不运行 `shadowbot_sync_tool.py`，也不把影刀同步作为常规验证步骤。
10. 同一个结果已经通过正常业务流程获得后，不为了“保险”再次读取、再次扫描或用另一套逻辑重复确认；“TODO / 需运行验证”只保留给必须依赖真实影刀、WPS、浏览器或页面运行才能确认的问题。

## 禁止行为

1. 不擅自更换用户已确定或真实项目正在使用的实现路线。
2. 不隐藏副作用，不通过吞异常、静默失败或模糊返回值让主流程看起来成功。
3. 不为一次开发任务创建临时进度 Markdown；需要长期保留的业务规则和设计决策写入项目现有正式文档。

完成后简短说明修改内容、验证与同步情况，以及仍需运行验证的事项。未运行测试、同步或影刀编辑器内验证时必须明确说明。
