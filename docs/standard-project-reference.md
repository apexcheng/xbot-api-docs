# 影刀多数据源报表自动化：标准流程项目参考

本文指定一个真实影刀项目作为同类开发的首选流程参考，适用于“网页下载数据 → 写入同一目标工作簿 → 全部成功后统一保存 → 发送通知”的自动化项目。

## 适用场景

以下任务优先参考该项目：

- 新建多数据源报表自动化项目
- 重构多个下载脚本组成的完整业务流程
- 多个网页、店铺或平台数据写入同一个目标工作簿
- 任一数据源失败时不能保存部分结果
- 需要完整流程重试、统一保存、统一关闭和统一通知
- 需要将复杂流程写成初学者也能顺序阅读的代码

简单的单页面操作、单个 API 调用或单表处理，不必强行套用完整结构。

## 参考优先级

Agent 开发同类项目时按以下顺序判断：

1. 用户当前需求和验收标准。
2. 当前真实项目已有代码和业务规则。
3. 本标准参考项目的流程结构。
4. 知识库中的 API、市场指令和专题文档。

标准参考项目用于确定架构和执行顺序，不替代当前项目的真实页面证据。

## 标准文件结构

```text
run.py
config.py
tool.py
update_global_promotion.py
update_order_data.py
update_live_broadcast.py
update_selected_alliance.py
update_erp_shipment.py
其他 update_xxx.py
```

### `run.py`

只负责完整流程的统一编排：

```text
读取入口参数
→ 初始化或检查各平台登录状态
→ 打开目标工作簿
→ 检查只读状态
→ 按业务顺序调用各数据模块
→ 所有模块成功后写入更新时间
→ 统一保存
→ 统一关闭和清理页面
→ 最终发送一次成功或失败通知
```

主流程应自上而下连续阅读。不要用动态调度器、复杂映射或多层 `_run_xxx()` 把真实执行顺序藏起来。

### `update_xxx.py`

每个独立数据源一个模块，对外只暴露一个清晰入口，例如：

```python
def update_order_data(browser_profile, target_workbook):
    ...
    return True
```

入口参数只接收该模块实际需要的对象。通常包括浏览器 profile、已登录页面或会话、目标工作簿。

不要把所有配置和状态打包成大字典传入，也不要为了统一形式增加未使用参数。

### `tool.py`

只放稳定且确实复用的公共能力，例如：

- 获取下载目录
- 清空目标 Sheet 的数据区域
- 将二维数据统一转换为文本
- 日期值转换
- 验证码或解压密码读取
- 钉钉通知

只使用一次、代码很短或与单个业务强绑定的逻辑，应保留在对应模块中。

### `config.py`

只保存稳定配置。账号密码、Webhook、token 等敏感信息不得提交到公开仓库。

## 数据模块固定顺序

下载并覆盖目标区域的模块，优先按以下顺序编写：

```text
开始日志
→ 设置浏览器环境
→ 打开页面
→ 执行页面操作
→ 触发并等待下载
→ 校验下载文件路径
→ 打开源工作簿
→ 读取并校验数据范围
→ 获取目标 Sheet
→ 只清空目标数据区域
→ 统一转换为文本后写入
→ 关闭源工作簿
→ 返回 True
```

追加型数据源不清空旧数据，应先确定最后日期或最后数据行，再把新数据追加到下一行。数据已经最新时，可以记录日志并直接返回 `True`。

## 统一保存：禁止部分成功

目标工作簿只允许在所有必需数据模块都成功后保存。

主流程应明确检查模块返回值：

```python
if update_xxx(...) is not True:
    raise RuntimeError("xxx 模块未返回成功结果")
```

任一模块失败时：

- 不写入新的更新时间
- 不保存目标工作簿
- 放弃本轮内存修改
- 关闭目标工作簿
- 进入下一次完整流程重试

不要把每个模块各自保存设计成默认方案，否则会产生部分数据已更新、部分数据仍旧的混合状态。

## 完整流程重试

重试应覆盖完整业务流程，而不是只重试最后一个失败动作。

每次尝试都应重新执行：

```text
登录或初始化
→ 打开目标工作簿
→ 调用全部数据模块
→ 写更新时间
→ 保存
```

失败日志至少记录：

- 当前尝试次数
- 当前失败步骤
- `traceback.format_exc()` 完整异常堆栈

三次都失败后，发送一次失败通知并抛出最后一次异常。成功后立即停止后续重试。

## 通知规则

通知属于完整流程的最终结果，不应由每个数据模块分别发送。

成功通知建议包含：

- 执行时间
- 已更新的数据源
- 保存状态

失败通知建议包含：

- 执行时间
- 尝试次数
- 最后失败步骤
- 本轮已完成的数据源
- 最后异常信息

通知失败只记录 warning，不应把已成功保存的业务流程改判为失败。

## Excel 数据处理原则

### 只清空数据区域

根据目标 Sheet 的固定起始列和当前首空行、首空列清空数据内容，不要整表 `clear()`，避免删除公式、格式和其他业务区域。

### 写入前统一转为文本

下载报表中的商品 ID、订单号、链接 ID 等长数字写入 Excel 时可能丢失精度。写入前统一转换为文本，空值保持为空字符串。

### 区分覆盖型与追加型

- 覆盖型：先清空指定数据区域，再从固定单元格写入完整数据。
- 追加型：根据最后日期或最后数据行，只追加缺失日期的数据。

## 页面与下载处理原则

- 使用真实项目已有 XPath 和市场指令用法，不猜接口。
- 页面需要异步生成报表时，循环等待下载按钮；短超时未出现可刷新页面，整体设置明确截止时间。
- 下载完成后必须检查返回路径是否为空。
- 浏览器 profile、店铺切换和登录状态应由主流程或对应业务模块明确处理。
- 页面、下载、验证码、解压、表格写入等关键步骤都应有可定位日志。

## 参考边界

可以优先参考：

- 文件职责划分
- 主流程执行顺序
- 一个数据源一个入口模块
- 完整流程重试
- 全部成功后统一保存
- 统一通知
- 覆盖型和追加型数据写入方式
- 长数字文本写入
- 日志定位方式

禁止直接照搬：

- 账号、密码、token、Webhook
- URL 中的店铺或账号标识
- XPath、按钮文案和页面状态判断
- Sheet 名、起始列和写入区域
- 日期范围和时间口径
- 市场指令参数
- 当前项目中的临时注释、废弃模块和未完成业务

## 与最新知识库规则的关系

该真实项目是流程结构的首选参考，但项目中的个别历史写法可能尚未同步到知识库最新规则。

具体 API 参数、关闭方法、函数调用换行、异常处理和同步规则，仍以以下内容为准：

1. 当前用户需求
2. 当前项目根目录 `AGENTS.md`
3. 知识库根目录 `AGENTS.md`
4. `llms.txt` 定位到的最新 API 文档

不要因为参考项目中存在旧写法，就覆盖知识库已经明确修正的规则。

新建同类项目时，优先读取标准项目中的：

```text
run.py

与当前数据源最相近的 update_xxx.py
```
