# 多数据源报表安全边界

本文只适用于“多个必需数据源写入同一目标工作簿”的项目。单个 API、单个数据源或各自保存到独立文件的任务，不要机械套用。

## 不可破坏的结果边界

1. 所有必需数据源都成功后，才写入新的更新时间并保存目标工作簿。
2. 任一必需数据源失败时，不保存本轮内存修改，避免“一部分是新数据、一部分是旧数据”。
3. 重试覆盖完整流程：重新初始化、打开工作簿、执行全部必需模块、写更新时间并保存，不只重试最后一个失败动作。
4. 成功或失败通知在完整流程结束时统一发送，各数据模块不分别发最终结果通知。
5. 通知失败只记录 warning；不把已成功保存的业务结果改判为失败。

## 主流程

```text
读取入口参数
→ 初始化登录或会话
→ 打开目标工作簿
→ 按业务顺序执行每个必需数据源
→ 确认全部成功
→ 写入更新时间
→ 统一保存
→ 关闭工作簿和页面
→ 发送一次最终通知
```

主流程应从上到下直接阅读。不为了形式统一引入动态调度表、巨型 `context` 或多层 `_run_xxx()`。

## 数据源模块

独立数据源只在代码量较多、业务边界清楚且拆出后更容易阅读时建立模块。入口只接收实际需要的页面、会话、配置或目标工作簿，不传入包含所有状态的大字典。

成功协议只选一种：

- 成功正常返回，失败抛出异常；或
- 项目已有显式布尔协议时，主流程严格检查 `is True`。

不混用“部分函数抛异常、部分函数返回 `None`、部分函数返回布尔值”的成功判断。

## Excel 写入安全

- 覆盖目标区域前，使用本轮已读取的数据确认当前业务必需的表头、列映射、数据范围和目标区域，并按已确认的业务约定判断空结果是否允许覆盖；无法确认时停止该数据源，不清空旧数据。不增加重复读取或全量预检。
- 覆盖型数据：只清空约定的数据区域，不整表 `clear()`，避免删除公式、格式和其他业务区域。
- 追加型数据：先确认最后日期或最后数据行，只追加缺失数据。
- 商品 ID、订单号、链接 ID 等长数字写入前按文本处理，避免精度丢失。
- 下载步骤必须检查返回路径非空且文件存在，不把“已点击下载”当作“文件已可用”。

压缩包解压和解压后多文件目标识别见 [xzip.md](../xbot-api-docs/docs/xzip.md)。

Excel / WPS 具体 API 见 [excel.md](../xbot-api-docs/docs/excel.md)。

## 重试与日志

每次完整尝试开始时记录尝试次数和必要业务上下文；失败时在异常处理中记录当前业务步骤及 `traceback.format_exc()` 完整堆栈。成功后停止重试；达到项目规定的最大次数仍失败时，在最后一次失败对应的 `except` 中发送一次失败通知后直接 `raise`，需要增加业务上下文时使用 `raise ... from exc`，不要把异常保存到变量后脱离原 `except` 再重新抛出，也不要静默结束。

页面打开、下载等待、验证码处理、解压、工作簿写入和最终保存等关键阶段应有可定位日志；日志服务于定位当前业务步骤，不为了“完整”给每个简单赋值和基础调用都加日志。

页面、XPath、Sheet 名、写入区域、日期口径和市场指令参数仍以当前项目为准，不从本文猜测。
